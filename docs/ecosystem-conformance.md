# JVM-free HOCON Ecosystem Conformance

Conformance results for JVM-free HOCON parsers across five languages, measured
against the shared fixtures in this repository. Where
[`compliance-matrix.md`](compliance-matrix.md) tracks the four o3co
implementations at spec-item granularity, this file records the raw
fixture-pass results for the reachable third-party libraries under the same
method.

Each library parses every fixture `.conf` and emits resolved JSON, which is
compared against the fixture's `-expected.json` (generated by Lightbend's
reference implementation). Two corpora are reported:

- **Spec corpus (173)** — the o3co cross-impl fixtures under `testdata/hocon/<group>/`.
- **Lightbend suite (16)** — the upstream Lightbend fixtures that carry a `-expected.json`.

Measured **2026-10-16**, with all four o3co libraries at **v1.14.0**. Versions
are pinned per row; re-run when a listed library releases a new version. Two
third-party libraries released since the previous run (2026-07-15) and are
measured at their new versions: gurkankaymak/hocon (1.2.23 → 1.4.0) and
hocon-rs (0.1.3 → 0.2.0); every other third-party pin is unchanged because no
newer release exists. The spec corpus grew from 134 to 173 fixtures since that
run (the six empty-file fixtures, now folded in — see [Method](#method) — plus
fixtures added since July), so the counts are not directly comparable with the
July snapshot. Libraries are
listed alphabetically within each language.

## Method

One adapter per library — a CLI that reads a `.conf` path and prints the
resolved config as JSON to stdout — is driven over every fixture as an isolated
subprocess, and the output is compared to the fixture's expected JSON. The same
normalization is applied to every library:

- Object key order is ignored; arrays are order-sensitive.
- Numbers compare by value (`1` equals `1.0`); a JSON `string` is not equal to a
  JSON `number`.
- `null`-valued object keys are dropped before comparison, matching HOCON's
  "`null` == missing" semantics and Lightbend's own JSON renderer.
- A fixture's `.env` sidecar, where present (the `env-var-list` group), is
  loaded into the subprocess environment.

Corpus scope:

- **Empty-file group (6 fixtures)** — `empty-file/ef01`–`ef06` are part of the
  spec corpus from this run on. They were held out of the 2026-07-15 run
  because the o3co releases measured then (v1.8.0) rejected an empty or
  comment-only file, an S3.1 violation; Lightbend's `{}` is the correct spec
  reading (see [E10](extra-spec-conventions.md#e10)), and all four o3co
  libraries were fixed on 2026-07-23 (ts.hocon#153 / rs.hocon#146 /
  go.hocon#155 / py.hocon#11). All four pass the group at v1.14.0.
- **`.conf` inputs only** — the corpora contain every fixture whose input is a
  `.conf` with a `-expected.json`. The 30 expected outputs whose input is a
  `.properties` file (`properties-syntax/`, `properties-conflict/`) or an
  API-level `.yaml` scenario (`deferred-resolution/`) do not fit the
  one-`.conf`-in, JSON-out adapter contract and are not driven.
- **JVM system-property fixtures** — `test01` and `test03` in the Lightbend
  suite reference `${?java.version}` / `${?user.home}`, which resolve only
  inside a JVM. They stay in the Lightbend-suite count, which is why that
  column tops out at 14/16 for a non-JVM parser.

Run environment for this snapshot: Go 1.26.4, Rust 1.95.0, Node.js 26.0.0,
Python 3.11.15, Ruby 2.6.10 (macOS, arm64). o3co/py.hocon has the same import
name (`hocon`) as the third-party `hocon` distribution, so the harness installs
it into its own virtualenv.

Because the expected JSON is Lightbend-generated and the normalization is
uniform, the numbers measure each library's agreement with the Lightbend
reference implementation.
